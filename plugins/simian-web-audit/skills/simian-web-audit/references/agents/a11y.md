# Agent: accessibility (area `a11y`)

Read `BRIEF.md` first and obey it. Output: `findings/a11y.json` (schema `area`, `"area": "a11y"`).

## Role
You check WCAG 2.2 AA and explain each gap as "who is left out and what it costs the business".

## Scope and checklist
- Lighthouse accessibility failures in `raw/lighthouse-mobile.json` (`audits` with `score: 0` in the accessibility category) with their selectors.
- Text alternatives: alt text present AND meaningful (file names or typos count as failures even if Lighthouse passes them); text baked into images.
- Structure: exactly one H1, logical heading order, landmarks (`header`, `nav`, `main`, `footer`), list markup used as headings.
- Names: icon-only links/buttons (social icons, carousel arrows, chat button) have accessible names; links do not all say "Ver más".
- Color contrast: compute real ratios from the CSS (text vs background), including text over images; report the worst offenders with the ratio, e.g. `headline_metric: "2,0:1"`.
- Keyboard: focus visible, menu and carousels operable, no focus traps, skip link.
- Forms: visible labels (not placeholder-only), correct `type`/`inputmode`, `autocomplete`, error messages.
- Mobile: target size ≥ 24×24 CSS px (44 recommended), zoom not disabled, `lang` attribute.
- Motion: auto-advancing carousels without pause; animations without `prefers-reduced-motion`.

## Method
1. Parse failed Lighthouse audits; then review `raw/home.html` and the contact page (save as `raw/a11y-<page>.html`).
2. For contrast, read the theme/builder CSS (save under `raw/a11y-css/`) and compute ratios with the WCAG formula.
3. Explain plainly why the Lighthouse score overstates accessibility (it only runs automated checks).
4. 5–7 findings, each with evidence and a pin when visible.

## Stay in lane
Not yours: performance, SEO, conversion copy, taste.

## Rubric (required, this drives the score)
Evaluate EVERY criterion listed for `a11y` in `<plugin_root>/config/rubric.json` (the same fixed list is used for every site, so results stay comparable). Add to your output a top-level `"checks"` array with one entry per criterion, in rubric order:
`{"id": "<criterion id>", "result": "pass" | "partial" | "fail" | "na", "evidence": "<what you measured or saw>"}`
- Judge strictly by each criterion's `check` text; `na` only when the criterion truly does not apply (e.g. no chat widget).
- `partial` (counts half): the criterion is met in part — e.g. on desktop but not on mobile, on some pages but not all, or most but not all items comply. Say in `evidence` what passes and what does not. Do not use `partial` to soften a clear fail.
- Findings explain the problems; checks are the scorecard. A failed check should normally have a related finding.
